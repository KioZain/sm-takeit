# Движок плеера для мобильного приложения

Рабочий план. Ветка `webview-player`, сливается в `main` после этапа 8.

## Задача

Мобильное приложение должно показывать анимированные сеты с прозрачным фоном. Сеты
и анимации настраиваются в генераторе, поэтому пространство вариантов неограниченное:
только параметры анимации дают ≈280 комбинаций (8 узоров рельефа × 4 угла/грани ×
2 направления × 5 сглаживаний) до слайдеров, а расстановка роллов свободная.

Предрендеренные ролики под это не подходят: один сет × одна анимация = один файл.
Поэтому в приложение встраивается **рендерер, а не видео**: генератор отдаёт пресет
(несколько килобайт JSON), приложение рисует.

## Почему WebView, а не нативный порт

Сцена уже рисуется как SVG и работает в браузере. WebView даёт один плеер на обе
платформы вместо двух портов изометрии, порядка перекрытия и волны. Прозрачность
включается штатно: `isOpaque = false` на iOS, `setBackgroundColor(0)` на Android.

Нативный рендер (Skia) остаётся следующим шагом, если упрёмся в производительность.
К тому моменту плеер будет работающим эталоном для сверки.

## Главное архитектурное решение

**Плеер не повторяет логику сцены, а исполняет ту же самую.**

`buildIsoSceneModelFromState(state)` принимает обычный объект
`{ values, mediaAssets, timeline }` — это видно по тестовым фикстурам, где состояние
собирается вручную. Значит плеер может собрать **синтетический `IsoStateSource`**
из пресета и списка картинок, после чего вызвать те же функции, что и редактор:

```
пресет + картинки → IsoStateSource → withIsoLoopProgress(progress)
                                   → buildIsoSceneModelFromState
                                   → <IsoSceneLayers>
```

Отсюда следует, что плеер **не может разойтись** с генератором: расхождение означало бы,
что разошлись сами функции, а их держат 131 тест.

Нового кода — только адаптер пресета и оболочка плеера.

## Границы, которые нельзя нарушать

Проверено по подписанному манифесту `src/toolcraft/.toolcraft-manifest.json`:

| Файл | Статус |
| --- | --- |
| `index.html`, `vite.config.ts`, `tsconfig.json`, `playwright.config.ts` | подписаны |
| `src/main.tsx`, `src/router.tsx`, `src/styles.css`, `src/routes/*` | подписаны |
| `package.json` | не подписан, но 20 имён скриптов зафиксированы |

**Следствие:** плеер не может быть ни вторым входом основной сборки, ни маршрутом
приложения — оба пути требуют правки подписанных файлов.

Поэтому плеер живёт в отдельной папке `player/` в корне репозитория со своей сборкой.
Это легально: `check-toolcraft-code-health.mjs` сканирует только
`sourceRoots: ["src", "e2e", "scripts"]`, так что `player/` вне его области — там нет
ни бюджета строк, ни продуктового AST-барьера. Зависимость односторонняя:
`player/` импортирует из `src/app/iso/`, обратных рёбер нет.

## Этапы

Каждый этап заканчивается проверяемым результатом. Этапы 3 и 7 — точки, где результат
можно посмотреть глазами.

### Этап 0 — Ветка и план ✅

Ветка `webview-player`, этот документ.

### Этап 1 — Скорость как параметр генератора

Сейчас скорость в пресет не попадает: `ISO_WAVE_LOOP_SECONDS = 4` — это лишь
`defaultDurationSeconds` таймлайна, а пресет сохраняет только `values`. Плеер не узнает,
с какой скоростью крутить.

- Контрол скорости в `src/app/app-schema.ts` (секция «Рельеф»).
- Цель добавить в `ISO_PRESET_VALUE_TARGETS`, чтобы она ехала в пресете.
- Перегенерировать `app-defaults.json` и зашитые пресеты со значением по умолчанию.

**Формат пресета после этого этапа считается замороженным** — плеер строится против него.

Проверка: тесты пресетов, `ai:check`, контрол виден и меняет скорость волны в приложении.

### Этап 2 — Адаптер «пресет → сцена»

Новый модуль `src/app/iso/iso-preset-scene.ts`:

```ts
createIsoPresetState(preset, images) → IsoStateSource
```

где `images: { name, url, width, height }[]` — картинки от хоста с их натуральными
размерами. Размеры обязательны: `IsoObjectRecord.size` участвует в раскладке, а пресет
его не хранит (там только `anchor`, `footprint`, `scale`, `name`).

Проверка: для каждого зашитого пресета модель сцены, собранная адаптером, совпадает
с моделью, собранной через состояние редактора. Это прямой тест на неразъезжание.

### Этап 3 — Скелет плеера, статичный кадр 👁 **можно смотреть**

```
player/
  index.html
  vite.config.ts
  src/main.tsx
  src/player-root.tsx
```

Монтирует `IsoSceneLayers` с зашитым пресетом, фон прозрачный, сетка скрыта.

Проверка: открыть сборку в браузере поверх цветной подложки, снять скриншот,
убедиться что альфа настоящая, а не белый прямоугольник.

### Этап 4 — Анимация и скорость

- Цикл на `requestAnimationFrame`, прогресс петли из `withIsoLoopProgress`.
- Скорость из пресета, пауза по `visibilitychange` и когда плеер вне экрана.
- Без таймлайна Toolcraft — плеер ведёт время сам.

Проверка: покадровая детерминированность (один и тот же прогресс даёт один и тот же
кадр), отсутствие дрейфа на длинной петле, 60 fps в профайлере.

### Этап 5 — Публичный API для хоста

`player/src/api.ts`, глобальный объект:

```ts
TeikidoPlayer.load({ preset, images, speed?, autoplay? })
TeikidoPlayer.play() / pause() / setSpeed(x) / setProgress(t) / destroy()
TeikidoPlayer.on("ready" | "error", handler)
```

Плюс `.d.ts` для интеграторов. Ошибки наружу в явном виде: не нашлась картинка,
битый пресет, неподдерживаемый формат.

Проверка: демо-страница в `player/demo/`, дёргающая весь API, включая смену пресета
на лету.

### Этап 6 — Сборка под WebView

- Один самодостаточный HTML: JS и CSS инлайном, внешних запросов нет.
- Картинки приходят от хоста (`data:` или `file://`), плеер их не качает.
- Выключить прокрутку, выделение текста, зум, подсветку тача, контекстное меню.
- Зафиксировать бюджет размера бандла.

Проверка: открыть собранный файл по `file://`, убедиться что работает без сервера;
замерить размер.

### Этап 7 — Проверка в настоящем WebView 👁 **финальная приёмка**

- Минимальный WKWebView-хост под iOS Simulator, `isOpaque = false`,
  `backgroundColor = .clear`.
- Скриншот плеера поверх цветного фона приложения — доказательство прозрачности
  на реальной платформе, а не в браузере.
- Замер частоты кадров на симуляторе.

Android проверяется по той же схеме, если будет доступ к эмулятору; иначе инструкция
по настройке остаётся в документации и проверяется на стороне мобильной команды.

### Этап 8 — Документация и слияние

- `player/README.md`: как встроить в iOS и Android, как отдать картинки, как подать
  пресет, что делать с прозрачностью и производительностью.
- Запись в `CHANGELOG.md` и `docs/toolcraft/agent-worklog.md`.
- Мердж `webview-player` → `main`, пуш. Деплой генератора Action сделает сам.

## Риски

**Производительность на слабых устройствах.** SVG с полусотней `<image>` плюс
пересчёт рельефа каждый кадр. Если не вытянет — первым делом резать частоту
пересчёта рельефа, затем переходить на canvas, и только потом на нативный рендер.
Замерять на этапе 7, не раньше.

**Размеры картинок.** Пресет их не хранит, а раскладка от них зависит. Если хост
отдаст картинки без размеров, плеер должен их измерить после загрузки — и до этого
момента не рисовать, иначе будет скачок раскладки.

**Прозрачность в Android WebView** требует `setBackgroundColor(0)` и иногда
отключения аппаратного ускорения на старых версиях. Проверяется только на устройстве.

**`player/` вне области code-health** — это и свобода, и риск: там не действуют ни
бюджет строк, ни барьер импортов. Дисциплину держим вручную, модули оставляем мелкими.

## Открытые вопросы

- На чём написано мобильное приложение — нативные Swift/Kotlin, React Native, Flutter?
  От этого зависит, как именно хост отдаёт картинки и пресет.
- Нужен ли плееру экспорт кадра (кнопка «сохранить» внутри приложения), или он только
  проигрывает.
